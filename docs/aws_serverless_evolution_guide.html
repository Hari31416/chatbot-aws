1. System Architectural Overview

A high-performance serverless chatbot requires balanced design patterns. This guide traces the structural milestones and configuration details of a hybrid serverless system deployed on AWS. The application uses a combination of API Gateway and direct Lambda Function URLs to handle distinct traffic profiles.

Transactional metadata reads are fast. In contrast, large language model chat generation demands long-running, chunk-by-chunk stream delivery. Standard API Gateway HTTP APIs enforce a strict 6 MB payload limit and buffer all outgoing responses. They wait for the backend to complete execution before returning any data. This buffering introduces significant user latency when waiting for full completions.

To bypass these constraints, this architecture implements a dual-routing pipeline. All standard REST operations (loading histories, deleting conversations, checking system heartbeats) route through API Gateway HTTP APIs with edge-level Cognito JWT validation. Real-time chat streams bypass the gateway entirely. They route through a direct Lambda Function URL configured with RESPONSE_STREAM invocation mode and AWS Lambda Web Adapter. This design flushes tokens to your client instantly.

2. The 9-Stage Infrastructure Evolution

This project transitioned from a single-tier API Gateway endpoint to a decoupled, streaming architecture. Tracing the engineering stages reveals how key bottlenecks were identified and bypassed.

Stage 1: FastAPI + Mangum Core

The project began with a unified FastAPI server wrapped inside a Mangum ASGI adapter. The backend mapped to an API Gateway proxy route (/{proxy+}). This provided simple REST paths. However, it was limited by synchronous response cycles.

Stage 2: Direct S3 Static Web Hosting

Initial attempts used a CloudFront CDN to cache static assets. Unfortunately, CDN propagation lag (5 to 15 minutes) stalled active iterations. We simplified the stack by deleting CloudFront and hosting the compiled React files directly inside an S3 website bucket.

Stage 3: Cognito Authentication

Security required a solid identity pool. We added Cognito User Pools and configured a Cognito Authorizer directly on the HTTP API. However, this introduced immediate browser blocking. Unauthenticated preflight OPTIONS calls were blocked before hitting our backend.

Stage 4: CORS Preflight Split

To bypass preflight blocking, we split API Gateway routes. We explicitly declared REST endpoints under Cognito authorization but left the OPTIONS method unmapped. API Gateway now responds to preflights natively, bypassing authorization.

Stage 5: Secure Gemini vision

Integrating Gemini 3.1 Flash required handling multimodal inputs. To secure keys without plain-text template exposures, we integrated SSM Parameter Store. Decryption occurs during warm starts inside our database layer.

Stage 6: Costing Boundaries

High-volume testing threatened to exhaust free quotas. We modified the CloudFormation template to enforce a strict 7-day log retention rule on CloudWatch. We also pinned DynamoDB capacity to provisioned tier minimums.

Stage 7: Persistent History CRUD

Storing messages inside browser memory made chats fragile. We created a single-table DynamoDB layout to store user records. To bypass expensive, slow table scans, we projected a Global Secondary Index (GSI) called UserConversationsIndex.

Stage 8: Low-Latency SSE Streaming

Buffering latency was highly annoying. We integrated Lambda Web Adapter (LWA) and Lambda Function URLs. Because Function URLs bypass API Gateway edge authorization, we moved Cognito JWT validation directly inside our FastAPI backend using custom PyJWT layers.

Stage 9: Boot and CORS Conflict Fixes

Streaming deployments initially failed due to duplicate CORS headers injected by both Lambda and FastAPI. We stripped CORS rules from the SAM template. We also created a shell entrypoint (run.sh) to ensure clean virtualenv path boot.

3. Core Architectural Decisions

Designing high-performance serverless systems requires careful evaluation of trade-offs. The components below highlight the core choices between routing protocols and database sizing models.

Routing Layer: API Gateway v2 vs. Function URLs

Choosing how to expose compute resources dictates your streaming capability and authorization limits.

API Gateway HTTP APIs provide an excellent edge layer for standard metadata operations.

  • Edge Authorization: Integrates directly with Cognito User Pools. Rejects unauthenticated calls before invoking your compute function, saving Lambda costs.
  • Buffering Bottleneck: Strictly buffers outbound responses. It waits for the full payload before transmitting, rendering chunked Server-Sent Events impossible.
  • Payload Limit: Enforces a hard 6 MB payload limit on requests and responses.
  • Timeout: Restricts connections to a maximum of 29 seconds.

Lambda Function URLs with LWA provide a direct gateway to chunked streaming capabilities.

  • True Streaming: Bypasses buffering layers entirely. Flushes tokens to the client with sub-150ms Time-to-First-Byte.
  • Expanded Limits: Bypasses API Gateway's 6 MB constraint. Supports payloads up to 20 MB and keeps connections alive for up to 15 minutes.
  • No Edge Auth: Lacks integrated Cognito layers. Token validation must occur in-app using custom JWT middleware.
  • Dual Routing: The system combines both routing types. Standard REST paths use API Gateway, while streaming calls use FURLs.

Database Billing: Provisioned vs. On-Demand

DynamoDB billing models heavily impact operational costs.

Provisioned capacity maps resources to explicit performance parameters.

  • Always Free Eligibility: Qualifies for the AWS Always-Free Tier when pinned to 5 RCU and 5 WCU. Database capacity remains 100% free forever for low-volume apps.
  • Billing Predictability: Monthly costs are locked. You never face surprise bills from massive spike volumes.
  • Throttle Risks: Sudden traffic spikes that exceed the 5 RCU threshold are throttled, slowing client requests.

On-demand capacity adjusts to traffic dynamically.

  • Instantly Scalable: Handles massive spike workloads automatically without throttle blocks.
  • No Free Tier: Forfeits the free capacity. AWS bills you for every single transaction from request number one.
  • Cost Risks: A rapid surge in automated traffic or search scripts can create massive surprise bills.

4. SAM Template Configuration Deep Dive

AWS SAM simplifies serverless infrastructure modeling. Declaring targeted configurations in template.yaml ensures secure operations and strict resource management.

Bypassing OPTIONS Preflight Authorization Blocks

Edge-level Cognito authorizers block standard browser preflight checks. Declaring specific HTTP methods while omitting the OPTIONS verb solves this issue. API Gateway answers preflight requests natively without requiring tokens.

template.yaml (CORS Route Splitting)
  ChatbotBackendFunction:
    Type: AWS::Serverless::Function
    Properties:
      Events:
        GetApiEvent:
          Type: HttpApi
          Properties:
            Path: /{proxy+}
            Method: GET
            ApiId: !Ref ChatbotHttpApi
        PostApiEvent:
          Type: HttpApi
          Properties:
            Path: /{proxy+}
            Method: POST
            ApiId: !Ref ChatbotHttpApi

Enforcing CloudWatch Log Expirations

By default, Lambda log groups never expire, which leads to silent storage fee accumulation. Declaring an explicit log group with a short retention period eliminates this cost vector.

template.yaml (Log Retention)
  ChatbotBackendFunctionLogGroup:
    Type: AWS::Logs::LogGroup
    Properties:
      LogGroupName: !Sub /aws/lambda/${ChatbotBackendFunction}
      RetentionInDays: 7

Optimizing Global Performance and Costs

Configuring functions globally to run on ARM64 Graviton processors lowers compute fees by 20% compared to x86. Allocating 512 MB of RAM provides a comfortable processing threshold for warm starts and SSE stream encoding.

template.yaml (Globals)
Globals:
  Function:
    Timeout: 30
    MemorySize: 512
    Runtime: python3.12
    Architectures:
      - arm64

How are these values calculated?

2. Lambda Compute Costs: Lambda uses 512 MB Graviton ARM64 execution rates ($0.0000133334 per GB-second). First 1M requests and 400,000 GB-seconds are free monthly.

Lambda Cost Formula
GB_Seconds = Total_Requests * (Duration_ms / 1000) * 0.5
Billable_GB_Sec = Max(0, GB_Seconds - 400000)
Compute_Fee = Billable_GB_Sec * 0.0000133334
Billable_Req = Max(0, Total_Requests - 1000000)
Request_Fee = (Billable_Req / 1000000) * 0.20
Total_Lambda_Cost = Compute_Fee + Request_Fee

6. Knowledge Check

Verify your understanding of these serverless integration boundaries and cost models.

Question 1: Why did direct S3 Static Website Hosting replace CloudFront CDN during early development cycles?
S3 website hosting is faster than edge CDN caches.
CloudFront propagation times take 5 to 15 minutes, slowing iteration.
CloudFront cannot support standard React React-Router files.
Correct! Deleting CloudFront removed caching propagation delays. Static assets are uploaded directly to S3 and reflect changes instantly.
Incorrect. While S3 is highly efficient, CloudFront edge delivery is theoretically faster. The change was made specifically to bypass development propagation lags.
Question 2: How was the Cognito authentication preflight OPTIONS blocking issue resolved?
By enabling credentials inside the client's axios request config.
By routing options queries through a separate Lambda authenticator helper.
By excluding the OPTIONS method from explicit API Gateway route declarations.
Correct! Excluding the OPTIONS route allows API Gateway to consume preflights natively. It answers using the API's global CORS configuration without verifying JWTs.
Incorrect. Custom axios or Lambda authorizer overrides do not resolve edge blocks. The split must occur inside the SAM routing block.
Question 3: Why is BillingMode: PROVISIONED highly cost-efficient for this application?
Provisioned tables locked to 5 RCU / 5 WCU qualify for the AWS Always-Free Tier.
Provisioned capacity disables storage charges for indexing user conversation logs.
Provisioned tables process queries faster than standard On-Demand tables.
Correct! The Always-Free Tier covers up to 25 RCU and 25 WCU for provisioned databases. In contrast, On-Demand billing incurs charges from your first transaction.
Incorrect. Storage charges remain identical across billing models. The advantage is entirely derived from Free Tier capacity allocations.
