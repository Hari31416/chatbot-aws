# Chatbot AWS — Clerk Authentication Architecture

This document details the serverless authentication system built using **Clerk** (external Identity Provider). The architecture leverages in-app JWT verification within the FastAPI backend using standard OIDC public keys (JWKS), coupled with the `@clerk/react` SDK on the React client.

---

## 1. Authentication Architecture

```
User (Browser / Clerk UI)  ───►  Clerk Auth Services (Session & Token Issuance)
            │                               │
            │ Token                         ▼ Returns ID Token (JWT)
            ▼
API Gateway / Function URL  ───►  Lambda Backend (FastAPI / Uvicorn)
                                            │
                                            ▼ verifies signature offline (JWKS)
                                  Resolves User ID (sub) & checks claims
                                            │
                                            ▼
                                  Loads conversation history from DynamoDB
```

---

## 2. Infrastructure Configuration

Unlike Cognito, Clerk resources are hosted externally, so we do not provision user pool tables via AWS SAM. Instead, we configure connection parameters in our environment variables and inject them into our SAM templates:

### Backend Parameter Injections (`template.yaml`)

We define the following parameters in our SAM template:

- **`ClerkIssuer`**: The OIDC Issuer URL of your Clerk instance (e.g., `https://accurate-moccasin-43.clerk.accounts.dev/`).
- **`ClerkJwksUrl`**: Optional URL to override JWKS key resolution (defaults to issuer-resolved `/.well-known/jwks.json`).
- **`ClerkAuthorizedParties`**: Comma-separated list of client origins (e.g., `http://localhost:3000`) allowed in the token's `azp` claim.

These parameters are mapped to global environment variables injected into all backend Lambda functions:

- `CLERK_ISSUER`
- `CLERK_JWKS_URL`
- `CLERK_AUTHORIZED_PARTIES`

## 3. Frontend Authentication SDK Integration

Our frontend React single-page application integrates Clerk using the official `@clerk/react` package:

### Clerk Provider Config (`main.tsx`)

Wrap the application roots in the `ClerkProvider` using your publishable key:

```tsx
import { ClerkProvider } from "@clerk/react";

const clerkPublishableKey = import.meta.env.VITE_CLERK_PUBLISHABLE_KEY;

createRoot(document.getElementById("root")!).render(
  <ClerkProvider publishableKey={clerkPublishableKey} afterSignOutUrl="/">
    <App />
  </ClerkProvider>,
);
```

### Authentication State & Token Injection

- The frontend utilizes the `useAuth()` hook to fetch current session details.
- To make secure backend calls, the React client retrieves a session JWT token using `getToken()` from Clerk and attaches it as a `Bearer <token>` inside the `Authorization` header for all requests.
- A dedicated `<ClerkAuthSync />` component synchronizes the active authenticated token and user metadata with the application state.

## 4. In-App Backend JWT Claims Verification

Because Lambda Function URLs bypass API Gateway's edge authorizer, token verification is handled consistently within the FastAPI backend using a custom dependency.

### `_verify_clerk_token(token, settings)`

Defined in [dependencies.py](file:///Users/hari/Desktop/sandbox/chatbot-aws/backend/app/dependencies.py), this function executes offline cryptographic validation:

1. **Unverified Decode**: Inspects the token claims to check formatting and extract the issuer (`iss`).
2. **JWKS Key Retrieval**: Fetches the JSON Web Key Sets (JWKS) from the Clerk issuer endpoint and caches them locally to avoid fetching keys on every request.
3. **Signature & Expiry Check**: Matches the token header key ID (`kid`) with a JWKS key, constructs the RSA public key, and verifies the cryptographic signature and expiration claims (`exp`) with clock skew tolerance.
4. **Authorized Parties Check**: Validates the authorized party (`azp`) claim against the `CLERK_AUTHORIZED_PARTIES` setting to verify the token was issued for our frontend.

### `get_current_user_id(request, settings)`

This dependency extracts the verified `sub` claim from the payload. This `sub` claim represents the unique user ID generated by Clerk, which we use to query conversation histories in DynamoDB.

## 5. Local Dev & Testing Bypass

When testing locally:

- Authentication is automatically bypassed if `CLERK_ISSUER` is not set.
- You can open the **Settings drawer** in the UI and enter any custom username (e.g., `tester@domain.com`).
- This will automatically override local headers and map DynamoDB messages under that custom tester ID, enabling rapid offline testing.
